# RuPost 竞品与差异化开发报告

**日期：** 2026-11-13
**范围：** 当前 `HEAD`（0.2.0）产品与代码审查结果；竞品能力按公开官方资料核验。

## 结论

RuPost 不应成为“又一个 Postman”、也不应把自己缩成“Rust 版 Hurl”。最具竞争力的定位是：

> **面向代码库的、本地优先的 API 活文档验证与故障复现工具。**

用户在 Markdown 或 `.http` 中写下接口说明和可执行断言；RuPost 在本地或 CI 中运行它们，并在失败时生成经过脱敏、可重放、可归因的证据包。文档是契约，失败是可移交的工件，而非一段难以复现的终端输出。

该定位利用项目已经具备的 Markdown 解析、变量和 Cookie 会话、DAG 批跑、Mock、WebSocket/SSE、快照回放、JSON/JUnit/HTML 报告、脱敏和规则/AI 分诊能力。下一步应该将这些能力收束为一个可靠的用户闭环，而不是继续横向堆叠协议或界面。

## 当前项目判断

### 已形成的资产

| 资产 | 现状 | 战略意义 |
| --- | --- | --- |
| 文档原生执行 | `.http` 与 Markdown `http` 围栏均可解析与执行 | 让接口说明、验收条件和可执行测试在同一文件中演进 |
| 流程测试 | 变量捕获、Cookie、`@depends-on` DAG、串/并行执行 | 覆盖真实登录与跨服务工作流，而不止单请求 |
| 失败证据 | JSON/JUnit/HTML 报告、执行快照、脱敏、回放 | 能把“失败”从瞬时日志变成可分享事实 |
| 诊断能力 | 网络时序、trace 锚点、失败钩子、确定性 AI 基线 | 让开发者从失败走向定位，而非只看到红灯 |
| 本地交互 | CLI、TUI、Web Workbench、Mock | 可以服务编写、调试和 CI 三种场景 |

### 质量前提

近期代码审查显示核心测试与 Clippy 门禁均可通过，但 Web Workbench 的 Cookie 和捕获变量目前放在全局 `AppState`，没有按浏览器会话隔离。启用局域网访问时，多个客户端可能共享认证态和捕获变量。这必须在任何 Web 工作台推广前修复。

同时，`tests/verify_features.sh` 会掩盖一处套件执行失败并用文件名判断成功，且会终止当前用户的所有 `rupost` 进程。它不能作为发布可信度的依据，应该先改为临时端口、PID `trap` 清理及严格的退出码/语义断言。

## 竞品格局

| 类别 | 代表产品 | 已占据的用户预期 | 对 RuPost 的含义 |
| --- | --- | --- | --- |
| API 平台 | Postman | Collection、云同步、CLI/CI、监控、AI、协作生态 | 不做云工作区或平台功能的追随者；保留导入/导出与 CI 互操作 |
| Git-native 客户端 | Bruno | 本地优先、纯文本集合、Git 审查、多协议、桌面/IDE 使用 | “文件在仓库里”本身已不是差异点；RuPost 必须赢在文档语义和失败闭环 |
| 文本化 HTTP 测试 | Hurl | 轻量单二进制、请求链、变量捕获、断言与 CI | 不能只宣传 `.http` DSL；应突出 Markdown 活文档、可重放证据与调试链路 |
| API 全生命周期平台 | Apifox | 文档、Mock、自动化测试和团队协作的一体化工作台 | 不复制团队 SaaS；将本地文档变为可信回归资产，适合受限网络或代码优先团队 |
| 性能测试 | Grafana k6 | JavaScript 脚本、负载模型、阈值、指标与 SLO | 不自建压测引擎；未来只做“从 RuPost 工件导出到 k6”的桥接 |

Postman 的 CLI 已覆盖 collection 的终端与 CI 运行，并将结果与其平台同步；Bruno 已将 Git-native、local-first 和多协议作为核心卖点；Hurl 已支持纯文本请求链、变量捕获和断言。对应地，RuPost 的胜负不在请求能否发出，而在失败后是否能低成本、安全地被他人重现和理解。

来源：[Postman CLI](https://www.postman.com/product/postman-cli/)、[Bruno API Client](https://www.usebruno.com/product/api-client)、[Hurl Manual](https://hurl.dev/docs/manual.html)、[Apifox 自动化测试](https://docs.apifox.com/automated-testing)、[Grafana k6 API load testing](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/)。

## 差异化战略

### 核心承诺：可验证文档到可复现故障

以一个连续工作流替代零散功能清单：

```text
Markdown / .http 文档
        |
        v
本地或 CI 执行（变量、会话、DAG、协议）
        |
        +-- 成功：更新可读报告与契约状态
        |
        +-- 失败：脱敏快照 + JSON 报告 + trace 锚点
                                  |
                                  v
                        本地重放、规则归因、可选 AI 辅助
```

差异化不是“AI 自动写测试”。AI 应始终是受脱敏、配额、确定性基线约束的诊断增强层；即使无网络、无密钥，核心执行、报告和失败归因仍可交付确定结果。这一安全姿态比单纯的 AI 生成功能更适合企业内网和生产排障。

### 三个用户可感知支柱

1. **活文档验收：** Markdown 页面即接口说明又是可运行验收；Pull Request 既审文案也审断言与运行结果。
2. **复现包：** 一次失败输出最小、脱敏、可提交或可附到 issue 的工件，保留请求、期望、实际、时序、trace 与重放信息。
3. **本地诊断：** 工件无需云端即可回放、替换目标环境、比较差异、聚类失败原因；AI 仅在用户显式配置后辅助解释。

## 开发路线

### Phase 0：可信底座

目标：让任何“本地优先、安全诊断”的承诺可被相信。

- Web Workbench 为每个浏览器会话隔离 Cookie、变量和生命周期；默认 TTL、容量上限与显式清除。
- 修复特性脚本：临时端口、`trap` 清理、无 `killall`、严格检查命令退出码和响应语义。
- 将 `make test-web` 纳入 CI；为双客户端会话隔离增加真实 HTTP 集成测试。

验收：第二个客户端不能读取、复用或覆盖第一个客户端的 Cookie/捕获变量；脚本故意让套件失败时必须返回非零。

### Phase 1：故障复现包 MVP

目标：把已经存在的报告、快照、脱敏和回放能力组织成稳定的单一交付物。

- 定义版本化、机器可读的 `incident` manifest，引用现有快照和 JSON 报告，不复制协议执行逻辑。
- 提供一个明确的单命令入口，将失败运行产出压缩为目录：脱敏请求/响应摘要、断言差异、时序、trace 锚点、重放说明和环境要求。
- 将导出策略默认设为安全：凭据与敏感值不进入工件；未脱敏或无法确认安全时显式失败而非静默写出。

验收：另一台无历史状态的机器只凭复现包即可针对指定 `--target` 得到同类失败或明确的环境差异。

### Phase 2：文档契约门禁

目标：让团队在 Pull Request 中看到“接口说明是否仍被实现满足”。

- 为 Markdown 块建立稳定请求 ID 与来源行号，报告精确指向文档位置。
- 增加文档级契约摘要：本次通过、失败、跳过与相较基线的契约漂移；只处理确定性字段，动态字段沿用已有忽略与掩码策略。
- 提供 CI 友好输出：JUnit/JSON 保持稳定 schema，终端输出保持面向人类。

验收：接口响应破坏文档声明时，CI 与 HTML/JSON 报告都能定位同一 Markdown 区块和断言。

### Phase 3：互操作，而非重复建设

目标：接入用户已有工具链而不承担其产品面。

- 优先 OpenAPI 导入和测试文档生成；导入结果保留为可审查的 Markdown/`.http`，而非私有二进制集合。
- 优先输出可用于 k6 的场景草稿或可供 k6 消费的数据，不在 RuPost 内实现虚拟用户、分布式调度和指标数据库。
- 保持 curl、HTTPie、JUnit、JSON 等开放出口，降低迁移成本。

## 明确不做

- 不构建账号、团队空间、云同步、监控 SaaS 或通用 API 市场。
- 不追求 Postman/Bruno 的 GUI collection 管理功能对等。
- 不在核心执行链引入不可预测的 AI 决策。
- 不自建 k6 类负载发生器、指标平台或 JavaScript 脚本生态。
- 不为尚无用户需求的协议或插件面扩大公开 API。

## 成功指标

| 指标 | Phase 1 目标 | Phase 2 目标 |
| --- | --- | --- |
| 失败到首次可重放的时间 | 少于 2 分钟 | 少于 1 分钟 |
| 复现包在干净环境中的成功率 | 90% 以上 | 95% 以上 |
| 工件中的敏感信息泄漏 | 0 个已知案例 | 0 个已知案例 |
| Markdown 文档块可由 CI 执行的比例 | 30% 以上 | 60% 以上 |
| 无 AI 配置时的核心工作流可用性 | 100% | 100% |

## 下一步决策

建议立即执行 Phase 0，并在其通过后将“故障复现包 MVP”作为唯一新增产品主线。它复用当前高价值资产、开发面最小、与竞品差异最清晰，也为后续的文档契约门禁和 k6 互操作提供了可靠基础。
